# 次段階: setup 一度、起動ワンコマンド

この文書は PR #1 時点の提案記録です。Go コアの現在の実装・検証・未達点は [Setup と起動](setup-once-core.md) を参照してください。

これは設計提案で、現 CLI に資格情報保存や接続自動登録を追加したものではありません。

## 現コードの差分

setup は runtime と端末設定を準備し、Windows 所有者・許可ルートを記録します。API キーの入力・保存・Tunnel 作成・プラグイン登録は行いません。start が毎回マスク入力するため、現在の実装は新しい操作要件を満たしません。プラグイン/接続を登録する API 呼び出しもありません。

## 最小の拡張案

1. setup のローカル wizard で端末名、許可ルート、接続先を確認し、API キーを一度だけマスク入力する。
2. 本人が同意した OS のユーザー用資格情報保管庫へ、その端末の runtime key だけを保存する。非秘密の device.json には保管参照を置き、キーを JSON/Git/コマンド引数へ保存しない。Windows 資格情報マネージャーを候補とし、変更・削除も同じ端末の該当レコードだけを対象にする。
3. 共通の接続/プラグイン定義へ端末の endpoint と表示名を登録する。CLI に既存の登録 API 実装はないため、対象アプリの公式な登録経路を確認する。自動作成できない場合は、一度だけ必要なアプリの登録/承認操作を setup 内の案内へまとめる。未確認の API を推測して実装しない。
4. setup が既定 profile と固定版 launcher を準備し、以後 `xpotato-mcp-tunnel start` だけで起動する。所有者・非管理者・許可ルート・runtime を検証した後に保管庫からキーを読み、子プロセス環境へだけ渡す。キー不在時は setup の修復を案内し、起動ごとの入力を通常フローにしない。

配布の npx と毎回の起動経路は別に設計できます。npx を setup の入口にしても、以後は固定版のローカル launcher を使えば毎回の取得や長い private Git ref 指定を避けられます。自動起動サービスや OS 権限変更を導入する必要はありません。配布・コマンド公開方法は別途レビューします。

## 複数端末

共通 CLI を再利用し、端末ごとに profile、所有者、許可ルート、資格情報参照、異なる Tunnel ID を持たせます。端末ごとの新しいアプリコードは不要です。--device はローカル名であって、アプリ側の登録機能ではありません。複数接続を一つのプラグインへまとめられるかは対象アプリの対応に従い、端末追加だけで自動発見できるとは扱いません。

## 次の実装前に必要な範囲

実キーの永続保存はまだ行いません。保管先・ユーザー範囲・端末ごとのレコード・保存/置換/削除操作を具体化した同意を得てから実装します。接続/プラグインの実作成も公式経路と対象を確認してから行います。merge の許可は、これらの新しい資格情報・外部登録操作を含めた許可とは扱いません。

まず mock の credential adapter と registration adapter で、setup 再開・二重登録防止・キー不在・他ユーザー拒否・起動時の入力不要・出力へのキー混入防止を確認し、実保管や登録は本人の操作で受け入れ確認します。
